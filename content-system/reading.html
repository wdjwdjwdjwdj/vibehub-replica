网络与接口入门

APIAPI

程序之间的服务窗口：按约定的格式要，按约定的格式给。

什么时候会碰到

小程序取天气、网站用微信登录、前端拿后端数据——两个程序互相要东西，走的都是 API。

讲透

API 的本体不是那个网址，是约定：传什么参数、返回什么结构、错了给什么码，全写在接口文档里。所以字段拼错、类型不对，服务器直接拒单——多数「接口坏了」其实是「请求没按约定来」。还要注意 200 只代表送达，业务失败藏在响应正文里，得单独判断。

想深挖？进阶层（类比边界 · 设计权衡）

「接口」不止是网址那一层：手机 App 调相机、读通讯录，走的也是 API。只要是两个程序之间约定好的调用方式，都算 API——Web API 只是新手最先打交道的那一种。看懂这层，以后看到「系统 API」「开放 API」就不会慌。

跟着做一遍

先打开 api.github.com/users/octocat 亲眼看一次真实返回的 JSON。然后在 Claude Code 里说：用 fetch 请求这个接口渲染成卡片，失败时显示重试按钮——盯着它怎么写错误分支，对照文档核对。

常见误解与坑

✗API 就是一个网址。
✓网址是门，约定才是 API：参数、返回结构、错误码，全在文档里。
✗返回 200 就是成功。
✓200 只是 HTTP 层通了。密码错误这类业务失败写在正文里，要单独判断。
✗API 是后端的事。
✓前端天天在调：参数对不对、失败怎么兜底、加载中怎么展示，都是前端的活。

快速自测

调登录接口返回 200，但用户没登录上。最可能的原因？

200 只说明请求送达。密码错误这类失败在正文的字段里，要单独判断。

复制给 AI 的说法

这是接口文档和我的代码。帮我核对参数是否符合约定，并补上失败时的兜底处理。

A service window between programs: ask in the agreed format, get the agreed format back.

什么时候会碰到

A mini-program pulling weather, a site logging in via WeChat, a frontend fetching user data — any time two programs trade data, an API is the contract.

讲透

The API is not the URL; it is the agreement — which parameters, what response shape, which error codes — all written in the docs. That is why a misspelled field gets your order rejected: most 'the API is broken' turns out to be 'the request broke the contract'. And 200 only means delivered; business failures hide in the body and need their own check.

想深挖？进阶层（类比边界 · 设计权衡）

'Interface' reaches beyond URLs: when a phone app uses the camera or reads contacts, that is an API too. Any agreed way for two programs to call each other counts — Web APIs are simply the kind beginners meet first. Seeing this layer, 'system API' and 'open API' stop being intimidating.

✗An API is a URL.
✓The URL is the door; the API is the contract — params, shape, error codes, all in the docs.
✗A 200 means it worked.
✓200 clears the HTTP layer only. Wrong-password lives in the body and needs its own check.
✗APIs are backend work.
✓Frontend calls them all day: params, failure fallbacks, loading states.

现代前端入门

ComponentComponent

界面上可复用的一块：写一次，换参数到处用。

什么时候会碰到

同一个按钮在 20 个页面出现，改圆角要手改 20 遍——该抽组件了。

讲透

组件把一块界面和它的行为打包，用参数决定显示什么：一个月饼模具，换馅压不同月饼。页面由组件拼成。什么时候抽？土标准：同一段结构被复制到第二处，就抽。拆过头参数爆炸、读代码要跳七八个文件，一句话说不清用途的别拆。

想深挖？进阶层（类比边界 · 设计权衡）

也有不该抽的时候：只有一处使用、看不到复用前景的，抽出来只是多一层跳转。更稳的节奏是先让代码重复一次，第三次出现再抽——宁可晚抽，不要早抽。早抽的组件常常把参数猜错，返工更贵。

跟着做一遍

让 Claude Code 把项目里重复三次以上的按钮抽成 Button 组件（参数：文字、类型、点击事件），迁移完再数一次：改个圆角要动几处代码。这个数字就是收益。

常见误解与坑

✗一个组件必须一个文件。
✓只是习惯。小组件同文件共存完全合法，文件边界不决定拆分粒度。
✗组件是 React 专属。
✓Vue、Svelte、Web Components 都有，写法不同，思想一样。

接下来弄懂谁

state组件内部会变的数据就是状态frontend组件是现代前端的组织单位html组件最终渲染成 HTML

快速自测

同一按钮样式在 12 个页面，要求全改圆角。成本最低的做法？

组件的价值在这一刻兑现：样式集中一处。字符串替换碰不到结构差异。

复制给 AI 的说法

这段按钮结构在多个页面重复。抽成组件（参数：文字/类型/点击），给迁移步骤。

A reusable piece of UI: write once, re-parameterize everywhere.

什么时候会碰到

The same button on 20 pages and a radius change needs 20 hand edits — time to extract a component.

讲透

A component bundles a piece of interface with its behavior, props deciding what it shows: one mooncake mold, different fillings, different cakes. Pages are assembled from components. When to extract? The working rule: the moment the same structure gets copied a second time. Over-splitting explodes props and scatters reading across files — if you cannot describe it in one sentence, keep it merged.

想深挖？进阶层（类比边界 · 设计权衡）

There is also a time not to extract: used once with no reuse in sight, a component merely adds a hop. The steadier rhythm is letting code repeat once and extracting on the third appearance — extract late, not early. Early components often guess their props wrong, and rework costs more.

跟着做一遍

Ask Claude Code to extract any button repeated three or more times into a Button component (props: label, variant, onClick), then count how many places a radius change touches. That number is the payoff.

常见误解与坑

✗One component must equal one file.
✓Just a habit. Small variants can share a file; file boundaries do not set granularity.
✗Components are React-only.
✓Vue, Svelte, Web Components all have them — different syntax, same idea.

接下来弄懂谁

stateData a component changes over time is statefrontendComponents are the organizing unit of modern frontendhtmlComponents ultimately render HTML

快速自测

One button style on 12 pages; design wants rounder corners everywhere. Cheapest path?

This is the payoff moment: the style lives in one place. String replace misses structural differences.

复制给 AI 的说法

This button markup repeats across pages. Extract it into a component (label/variant/onClick props) and give me the migration steps.

AI 协作入门

Context WindowContext Window

AI 一次能看到的全部内容上限：对话、文件、提问，挤同一个窗口。

什么时候会碰到

聊久了它忘了你开头定的要求、大文件总结报错、想让它读完整个项目被拒——都是窗口满了。

讲透

窗口是模型单次能处理的 token 总量，像一张书桌：摆得下的才看得见。你的消息、贴的文件、它的回答都在往桌上放；满了，最早放的先被收走。长对话「忘事」不是记性差，是那份资料出了视野。收拾办法只有两种：清掉不重要的，或把大文件压成摘要再放回。

想深挖？进阶层（类比边界 · 设计权衡）

窗口大不等于能一口气塞下整个代码库：塞进十万个 token 的代码，模型看得过来但注意力会摊薄，关键处容易看漏。真正管用的思路不是「更大」，而是「更会挑」——先给相关文件，其余只给文件名让它自己开口要。这就是上下文工程的起点。

跟着做一遍

在 Claude Code 让它读一个 50 行的文件答题，再换几千行的试一次，观察后者怎么应对。会话变长后跑一次 /compact（Claude Code 自带的整理命令），相当于主动收拾书桌。

常见误解与坑

✗窗口大，记忆就无限。
✓超出的部分被截断或压缩成摘要。「记得」只在窗口内成立。
✗塞进窗口就都会被认真读。
✓关键约束放开头或结尾，比埋在几千字中间可靠。

接下来弄懂谁

token窗口容量按 token 算context-engineering窗口是硬约束，上下文工程是应对方法conversation-history历史占窗口最快

快速自测

AI 忘了你最初定的「只用 TypeScript」。最省事的有效做法？

旧约束可能已出窗口。重贴或压缩把资料放回桌面；换模型找不回丢的内容。

复制给 AI 的说法

会话已经很长。下面几条是最关键的约束，先确认收到再继续；上下文吃紧就先总结进展。

How much an AI can see at once: history, files, and your question share one window.

什么时候会碰到

It forgets the rule you set at the start, chokes on a huge file, or refuses to read the whole project at once — the window filled up.

讲透

The window is the total tokens a model can process in one pass — a desk: whatever fits is what it can see. Your messages, pasted files, and its own replies keep landing on the desk; when it fills, the earliest items get cleared first. Long-chat amnesia is not bad memory, it is material leaving the desk. Two fixes only: clear what does not matter, or compress big files into summaries and put those back.

想深挖？进阶层（类比边界 · 设计权衡）

A big window is not an invitation to stuff in the whole codebase: with a hundred thousand tokens of code, attention gets thin and key lines slip past. The working idea is not 'bigger' but 'pickier' — relevant files first, file names for the rest, and let the model ask. That is where context engineering starts.

跟着做一遍

In Claude Code, have it answer questions about a 50-line file, then try a few-thousand-line one and watch how it copes. When sessions get long, run /compact — tidying the desk on purpose.

常见误解与坑

✗Bigger window, unlimited memory.
✓Overflow is truncated or summarized. 'Remembering' only holds inside the window.
✗Everything in the window gets read carefully.
✓Key constraints at the start or end beat being buried mid-text.

接下来弄懂谁

tokenCapacity is counted in tokenscontext-engineeringThe window is the constraint; context engineering is the craftconversation-historyHistory fills the window fastest

快速自测

The AI forgot your early 'TypeScript only' rule. Cheapest effective fix?

The rule likely left the window. Re-pasting or compacting puts it back; a bigger model cannot recover lost content.

复制给 AI 的说法

This session is long. Here are the constraints that matter most — confirm them first; if context is tight, summarize our progress.

部署上线入门

DeploymentDeployment

把你电脑上能跑的项目，变成别人打开网址就能用的服务。

什么时候会碰到

本地演示一切正常，发给朋友的链接打不开；作品要放进简历让人点开看——中间就差这一步。

讲透

部署是把构建产物发布到服务器：本地炒好的菜（项目）装进餐盒（npm run build 出的 dist 目录）、放上平台（托管服务），别人才点得到。规矩是改一次发一次——改了代码不重新构建发布，线上永远是旧版。静态页面交给静态托管就行；带后端的还要安排服务器、数据库和域名。

想深挖？进阶层（类比边界 · 设计权衡）

「改一次发一次」靠人手容易忘，于是有了自动发布：代码一推送，服务器自己构建上线，这套流程叫 CI/CD。首次上线还有两道新手最常卡住的坎：域名解析和 HTTPS 证书——每个都值得单独学，本站都有对应词条。

跟着做一遍

跑 npm run build，把 dist 目录交给静态托管（CloudBase 或 Netlify 都行），拿到公网地址用手机打开验证。再改一行文案重新发一次，亲身体会「改一次、发一次」的节奏。

常见误解与坑

✗本地能跑，线上就能跑。
✓环境不同：路径大小写、环境变量、接口地址都可能翻车，按线上配置验证一遍。
✗把整个项目文件夹传上去就行。
✓发的是 dist 不是源码。node_modules 又大又跑不起来。

接下来弄懂谁

environment-variable测试和生产的差异靠环境变量区分backend带后端的应用要多安排服务器和数据库http部署的终点是用户通过 HTTP 打开你的网址

快速自测

同事说「代码早改好了，线上怎么还是旧的」。最可能的原因？

线上只认最后一次发布的产物。不重新构建发布，改多少遍本地都白搭。

复制给 AI 的说法

带我走一遍完整部署：构建、发布到静态托管、手机验证，并列出以后每次更新要重复的步骤。

Turning a project that runs on your machine into something anyone can open at a URL.

什么时候会碰到

The demo works on your laptop, the link you sent opens to nothing, and the portfolio piece needs a URL — deployment is that missing step.

讲透

Deployment publishes your build output to a server: the dish cooked at home (your project) goes into a takeout box (the dist folder from npm run build), onto a platform (a hosting service), and only then can anyone order it. The rule is ship once per change — edit without rebuilding and the live site stays old forever. Static pages only need static hosting; a backend app also needs a server, a database, and a domain.

想深挖？进阶层（类比边界 · 设计权衡）

Shipping by hand on every change is forgettable, so automation exists: push the code and the server builds and ships by itself — that is CI/CD. First launches also hit two classic walls: domain DNS and the HTTPS certificate. Each deserves its own entry, and both are covered here.

跟着做一遍

Run npm run build, hand the dist folder to a static host (CloudBase or Netlify), open the public URL on your phone to verify. Then change one line of copy and republish — feel the 'change once, ship once' rhythm firsthand.

常见误解与坑

✗Runs locally, runs online.
✓Different environments: path case, env vars, API URLs can all break. Verify against production config.
✗Upload the whole project folder.
✓You ship dist, not source. node_modules is huge and useless on the server.

快速自测

A teammate says the fix was made long ago but the live site is still old. Most likely cause?

The live site serves the last published build only. Without a rebuild and republish, local edits never land.

复制给 AI 的说法

Walk me through a full deployment: build, publish to static hosting, verify on mobile, and list the steps to repeat on every future update.

部署上线入门

Environment VariableEnvironment Variable

从代码外部注入的配置：同一份代码，不同环境不同设置。

什么时候会碰到

本地连测试库、线上连生产库；密钥不能进 Git；测试站和正式站接口地址不同——全靠环境变量。

讲透

环境变量是程序启动时从外部读的配置，像空调旋钮：机器一样，温度随房间调。前端有条特殊规矩：Vite 只把 VITE_ 开头的变量打进产物——所以前端变量是公开的，密钥只能放后端。另外改了变量要重启服务或重新构建才生效，改完没反应多半是这个原因。

想深挖？进阶层（类比边界 · 设计权衡）

前端变量还有个时机关卡：注入发生在「构建」那一刻，不是用户访问那一刻——改了变量必须重新构建，线上才更新；后端是运行时读取，重启就生效。机制不同，排错路数也不同：前端变量不对劲，先问一句「重新构建了吗」。

跟着做一遍

项目根建 .env，写 VITE_API_BASE_URL=http://127.0.0.1:3000，代码里用 import.meta.env 读取显示在页面；再把 .env 加进 .gitignore，跑 git status 确认不会被提交。

常见误解与坑

✗密钥放前端环境变量里就安全了。
✓前端变量会打进产物，访客打开浏览器全看得到。密钥只放后端。
✗.env 提交到 Git 方便共享。
✓仓库只放 .env.example 模板。真文件留在本地和 CI。

接下来弄懂谁

deployment测试与生产的差异就是环境变量的差异backend密钥的安全存放点是后端git.gitignore 决定 env 文件进不进仓库

快速自测

第三方服务的 API Key 放哪里最安全？

前端的一切最终都在访客手里。Key 放后端、前端只调自己的接口，泄露面最小。

复制给 AI 的说法

帮我设计前后端的环境变量方案：区分测试生产、密钥不进 Git，并检查现有配置有没有泄露风险。

Config injected from outside the code: one codebase, different settings per environment.

什么时候会碰到

Local talks to a test database while production uses the real one; an API key must never reach Git; staging and live URLs differ — env vars carry all of it.

讲透

An environment variable is config the program reads from outside at startup — the dial on an air conditioner: same machine, different setting per room. The frontend has a special rule: Vite only bundles variables prefixed with VITE_, so every frontend variable is public and secrets belong on the backend. One more gotcha: changes need a server restart or a rebuild to take effect — no reaction after editing is usually this.

想深挖？进阶层（类比边界 · 设计权衡）

Frontend variables carry a timing trap: injection happens at build time, not when a user visits — so a change demands a rebuild before the live site moves. Backends read at runtime, where a restart suffices. Different mechanisms, different debugging: wrong frontend value, ask 'was it rebuilt?' first.

跟着做一遍

Create .env at the project root with VITE_API_BASE_URL=http://127.0.0.1:3000, read it via import.meta.env.VITE_API_BASE_URL and show it on the page; add .env to .gitignore, then run git status to confirm it will not be committed.

常见误解与坑

✗Keys are safe in frontend env vars.
✓Frontend variables ship in the bundle; any visitor can read them. Secrets live on the backend.
✗Commit .env for easy sharing.
✓Commit a .env.example template only. Real files stay local and in CI.

快速自测

Where should a third-party API key live?

Everything in frontend code ends up in visitors' hands. Key on the backend, proxy through your own API — minimal exposure.

复制给 AI 的说法

Design my env var setup: separate staging and production, keys never in Git, and audit my current config for leaks.

网络与接口入门

HTTPHTTP

浏览器和网站服务器之间传消息的规矩：你发一个请求，它回一个响应。

什么时候会碰到

手机上列表刷不出来、提交表单报错、页面一片空白——想弄清哪一步出了岔子，都要从 HTTP 查起。

讲透

你每打开一个网页，浏览器都在和网站那台电脑一问一答：你这边发一个「请求」，写明想干什么（GET 是拿东西，POST 是交东西）、要哪里的东西；对方回一个「响应」，附带一个结果代码和内容。代码 200 是办成了，404 是这个地址没这个东西，500 是对方自己出错了。HTTPS 就是加了密的 HTTP——不加密的话，你输入的密码在网线上是裸奔的。

想深挖？进阶层（类比边界 · 设计权衡）

「点餐」式一问一答有个天然短板：对方没法先开口找你。聊天软件的消息要靠服务器主动推——这正是 WebSocket 这类技术存在的原因。另外 HTTP 不记得你是谁，你每发一个请求都要重新亮明身份，登录状态靠 Cookie 这张「随身会员卡」另外维系。

✓那把锁的意思是：内容被加密了、对方身份被核实过。没有它，登录密码等于明文广播。

The rules between your browser and the website's computer: you ask, it answers.

什么时候会碰到

A list that will not refresh, a form that errors, a blank page — when something breaks, HTTP is where the investigation starts.

讲透

Every page load is a question and an answer between your browser and the website's computer. You send a request saying what you want (GET to fetch, POST to submit) and where; it answers with a result code and content. 200 means done, 404 means nothing lives at that address, 500 means their side tripped. HTTPS is the same conversation with encryption — without it, passwords travel the wires in the open.

想深挖？进阶层（类比边界 · 设计权衡）

The question-then-answer pattern has a built-in gap: the server cannot speak first. Chat apps need the server to push messages — that is exactly why WebSocket exists. HTTP also has no memory of who you are; every request re-states its identity, and login sessions ride on cookies, like a membership card you show each time.

跟着做一遍

Open any website in a desktop browser and press F12 — a developer panel appears. Click the Network tab and refresh: hundreds of rows appear, one per exchange. Click rows with red numbers starting 4 or 5 and read the server's reply on the right. This is step one whenever a page misbehaves.

常见误解与坑

✗A 404 means the website is broken.
✓404 means this particular address has nothing — usually a wrong link. The whole site being down is a different failure.
✗Got a 400? Just submit it differently.
✓400 means what you submitted itself is wrong, and the reply usually names the field. Changing the method makes a different mistake.
✗HTTPS is just a padlock icon.
✓The lock means encrypted content and a verified identity. Without it, your password is broadcast in the open.

AI 协作入门

PromptPrompt

你发给 AI 的任务说明：四要素齐不齐，直接决定产出质量。

什么时候会碰到

生成的页面和预期差远、答非所问、格式每次漂移——先查任务说明，别急着怪模型。

讲透

把 AI 当实习生布置任务：只说「做个登录页」是抽奖；写清目标、背景（给谁用、在什么项目里）、约束（技术栈、禁区）、验收（什么算完成），产出立刻稳。四要素顺序随意，缺哪块哪块出问题。长期规则放系统提示（AI 的默认规矩），一次性任务放普通消息，别混。

什么时候会碰到

The page misses expectations, answers go off-topic, format drifts every run — audit the task sheet before blaming the model.

讲透

Treat the AI like an intern: 'build a login page' is a lottery. 现代前端入门

StateState

页面里会变的那部分数据：数据一变，界面跟着变。

什么时候会碰到

点赞后变红的爱心、购物车里加减的数字、你打字时输入框里的字——页面上所有会动的东西，背后都是状态在驱动。

讲透

把静态页面想成一张印刷品：印完就定，动不了。状态就是页面里那块「白板」——写上去能擦、擦了能再写，而且界面每次都按白板上的最新内容重画。有一条关键规矩：改状态必须走正规入口（React 里是专门的更新函数）。绕过它直接改，等于在白板背面偷偷写字——前台展示墙看不到。

想深挖？进阶层（类比边界 · 设计权衡）

为什么直接改变量界面不刷新？React 像个只认登记处的记录员：只有走更新函数「登记」的改动，它才知道要重画屏幕；私下涂改它一概看不见。项目变大后白板还会不够用，于是拆成每个组件一块小白板、全局一块大白板——什么时候用哪块，是前端进阶的分水岭。

跟着做一遍

打开 Claude Code，输入：帮我写一个最简单的计数器网页，一个数字，加一减一两个按钮。跑起来后让它故意改成 count = count + 1（不走更新函数），再点按钮——数字纹丝不动。改回正规写法再点，数字动了。亲手做这 10 分钟，胜过读十篇文章。

常见误解与坑

✗状态就是数据库里的数据。
✓状态刷新一下就没了。要长期保存的数据得写到后端，那是另一条路。
✗所有数据都放进全局状态最好。
✓只有跨页面共享的才进全局。全局越干净，后面越好维护。

什么时候会碰到

A heart turning red, a cart number ticking, text appearing as you type — everything that moves on a page runs on state.

讲透

Picture a static page as a printout: fixed once printed. State is the whiteboard inside the page — write, erase, rewrite, and the screen redraws from whatever is on it now. One key rule: state changes must go through the official updater (a dedicated function in React). Editing the value directly is like scribbling on the back of the whiteboard — the front wall never shows it.

Why does a direct edit not refresh? React is a clerk who only reads the registry: changes 'filed' through the updater trigger a repaint; secret edits are invisible to it. As projects grow, one whiteboard stops fitting — teams split into a small board per component plus one shared big board. Choosing which to use is the real dividing line of frontend skill.

TokenToken

AI 读写的计量块：文字被切成小块处理，计费和上限都按块算。

什么时候会碰到

聊到一半提示上下文太长、账单随对话变长上涨、发现中文比英文占额度——都是 token 在起作用。

讲透

模型不按字读，先把文本切成块：常见汉字一到两块，生僻字和表情切得更碎。块数同时是两把尺子：API 按块计费，上下文窗口按块装量。同一段需求写得更省，就是直接省钱、省窗口，模型也更容易抓到重点——重复和废话稀释的不是 token，是你的关键要求。

想深挖？进阶层（类比边界 · 设计权衡）

✗一个汉字就是一个 token。
✓常用字约一到两块，生僻字更碎。要准确数字就上计数工具，别靠猜。
✗token 喂得越多模型越聪明。
✓窗口大只是装得多。质量看模型和提问，不看堆料。

The chunks AI reads and writes in: billing and context limits are counted in them.

什么时候会碰到

A context-too-long warning mid-chat, a bill that grows with the conversation, Chinese costing more quota than English — that is token accounting at work.

讲透

Models do not read characters; they split text into tokens first. A common Chinese character runs one to two tokens; rare ones and emoji split finer. The count is two rulers at once: API billing counts tokens, and the context window holds tokens. A tighter brief directly saves money and window space, and helps the model catch your point — repetition dilutes not just tokens but your key requirements.

想深挖？进阶层（类比边界 · 设计权衡）

The split follows neither words nor characters — it is a learned subword routine (BPE-family statistics): frequent combos stay whole, rare ones shatter. That is why rewording the same paragraph changes the count — a money-saving lever, and one source of long-prompt instability.

跟着做一遍

✗One Chinese character equals one token.
✓Common characters run one to two; rare ones split further. Count with a tool instead of guessing.
✗More tokens make the model smarter.
✓A bigger window only holds more. Quality comes from the model and the prompt, not the pile.
